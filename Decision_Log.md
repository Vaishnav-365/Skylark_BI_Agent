# Decision Log — Skylark Drones Monday.com Business Intelligence Agent

## 1. Project Approach

The solution was designed as a conversational Business Intelligence agent that retrieves live data from monday.com, processes it through a deterministic analytics layer, and uses an LLM to understand business questions and present the results in natural language.

The architecture separates **data retrieval, analytics, agent reasoning, and presentation** so that financial and business metrics are calculated deterministically rather than being generated by the LLM.

**Architecture:**

`Frontend → FastAPI → Agent Service → Analytics/Tools → monday.com`

The LLM is responsible for understanding the user's intent, selecting the appropriate tools, and communicating the results. Python analytics functions remain responsible for filtering and calculating business metrics.

---

## 2. Key Decisions and Assumptions

### Monday.com API instead of MCP

I chose the monday.com API for the integration because it provided direct, predictable access to the two required boards and allowed the application to retrieve all records dynamically. This also simplified authentication, pagination, normalization, and error handling within the backend.

The solution does **not hardcode the supplied CSV/XLSX data**. The imported monday.com boards are treated as the source of truth and are queried dynamically.

### Deterministic Analytics Layer

Business calculations were implemented as Python functions rather than asking the LLM to calculate financial values.

The analytics layer handles metrics such as:

* Deal counts and open deals
* Open pipeline value
* Deals by sector, owner, and stage
* Work-order counts and execution status
* Billed value
* Collected amount
* Outstanding receivables
* Sector/status filtering

This reduces the risk of arithmetic errors or hallucinated business metrics.

### Clear Separation of Deals and Work Orders

Deals and work orders represent different business datasets. The agent is instructed not to treat them as the same population.

For example, a Mining pipeline value represents sales-deal data, while Mining collections represent work-order data. When the user asks for a comparison, both metrics are explicitly identified by their source and meaning.

### Data Resilience

The input data was treated as real-world, potentially inconsistent business data. The backend includes normalization and handling for missing/null values so that incomplete records do not unnecessarily prevent analysis.

Where missing or incomplete information materially affects an answer, the agent is instructed to communicate the limitation instead of making assumptions.

### Filtering

The agent exposes controlled filters rather than allowing arbitrary LLM-generated data manipulation.

Deals can be filtered by:

* Sector
* Owner
* Deal status

Work orders can be filtered by:

* Sector
* Execution status

This allows founder-level questions such as sector-specific pipeline and collection queries to be answered using the same underlying analytics functions.

---

## 3. Agent and LLM Design

The agent uses structured tools for business-data access:

* Business overview
* Deal queries
* Work-order queries

The LLM decides which tools are required based on the user's question. Multiple tools can be used for cross-dataset questions.

For example, a question comparing Mining pipeline with Mining collections requires both the deal and work-order tools.

The system prompt explicitly instructs the agent to:

* Never invent business metrics
* Use tools for data-related questions
* Preserve tool-provided numeric values
* Avoid unsupported percentages and derived conclusions
* Distinguish between datasets
* Ask for clarification when ambiguity materially affects the result
* Communicate relevant data-quality limitations

This creates a deliberate separation between **LLM-based intent understanding** and **deterministic business computation**.

---

## 4. Interpretation of "Leadership Updates"

I interpreted the optional "leadership updates" requirement as a lightweight executive-summary capability rather than building a separate dashboard.

When asked for a leadership update, the agent gathers relevant business-wide metrics and presents them in a concise format containing:

* Overall pipeline
* Work-order activity
* Billed value
* Collections
* Receivables
* Key observations supported by the available data
* Relevant data-quality caveats

The feature is implemented through the same conversational agent and existing analytics tools rather than a separate hardcoded workflow. This keeps the interface simple while demonstrating how the system could support recurring management communication.

---

## 5. Frontend and Deployment Decisions

A lightweight HTML/CSS/JavaScript frontend was selected because the assignment primarily evaluates the BI agent rather than frontend framework complexity.

The interface provides:

* Conversational chat
* Suggested business questions
* Markdown rendering
* Tables for structured results
* Loading and connection states
* Responsive layout
* Leadership-update prompt

The backend is implemented using FastAPI and deployed separately from the frontend. The frontend communicates with the backend through the `/api/agent/chat` endpoint.

This separation keeps the architecture simple and makes the hosted prototype independently testable.

---

## 6. Trade-offs

### Simple frontend vs. full frontend framework

A vanilla HTML/CSS/JavaScript frontend was chosen instead of React or another framework. This reduced development time and dependencies while still providing the required conversational experience.

### Existing analytics vs. LLM-generated analysis

More sophisticated autonomous analysis could have been delegated to the LLM, but this would increase the risk of incorrect financial calculations. Deterministic analytics were therefore prioritized over maximum flexibility.

### API integration vs. MCP

Using the monday.com API required implementing the integration directly, but provided greater control over pagination, normalization, and error handling within the application.

### Concise responses vs. exhaustive reporting

The agent is instructed to provide concise founder-level answers instead of returning raw datasets. Detailed records remain available through the underlying API/analytics layer when required.

## 7. Testing and Validation

The solution was tested using representative business questions covering:

1. Overall pipeline
2. Sector-specific pipeline
3. Sector-specific collections
4. Cross-dataset comparison
5. Leadership update
6. Business-wide snapshot
7. Sector with no matching records
8. Overall business metrics

The final hosted prototype successfully returned the expected results for all eight tests.

The backend was also tested independently before frontend deployment, including health and agent endpoints.

---

## 8. Limitations and What I Would Do Differently With More Time

The current implementation focuses on the requirements and available datasets. With more time, I would improve:

* Historical/time-series analysis for questions such as quarterly pipeline trends
* More advanced business KPIs and forecasting
* More detailed data-quality reporting
* Richer visualizations for leadership updates
* Persistent conversation history
* Authentication and role-based access
* More comprehensive automated tests
* Monitoring and structured logging for production use
* More granular handling of monday.com API failures and rate limits

The current agent intentionally avoids claiming trends, forecasts, causes, or recommendations when the available data does not support them.

---

## 9. Final Design Principle

The primary design principle was **trustworthy business intelligence over generative flexibility**.

The LLM interprets the founder's question and determines what information is needed, while the application remains responsible for retrieving, filtering, and calculating the underlying business metrics. This reduces hallucination risk and makes the resulting answers more appropriate for business decision-making.
